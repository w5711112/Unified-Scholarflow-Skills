# Obsidian 核心论文精读 Callout 模板

保留论文标题与来源行中的下载链接、DOI、Zotero key、等级、状态和标点。唯一 `^block-id` 单独放在论文标题下方、主 Callout 之前；只有完成门槛通过后，才把来源行末尾的 `状态：待精读` 改为 `状态：已AI全文读`。

知识点总标题只写标准名称；第一层标题使用 `第一层｜直觉理解 | 一句话本质`，只用同领域的最简概念作比较，不用生活类比。

每篇论文只使用一个外层折叠 Callout。所有内层行都必须保留正确的 `>` 嵌套层级，避免出现两个独立蓝色/绿色块。

```markdown
### PAPER HEADING
^BLOCK-ID
> [!note]- **来源**：DOWNLOAD，DOI，ZOTERO PDF，GRADE，状态：待精读
> - **一眼记住这篇论文**：用 1–3 个完整句子写清“谁接收什么输入、按什么顺序处理、输出什么并交给谁”，再收束原理—结构—效果；不能用术语替代解释
>
> > [!info]- **作者与团队背景（外部信息，YYYY-MM-DD）**
> > - **一作/共同一作**：角色、学历、现机构/实验室/职称、研究方向、项目、代表成果、荣誉、会籍、Citations/H-index 与来源日期；无法核验项明确写出
> > - **通讯作者**：同上，全部通讯作者逐人列出
> > - **来源与边界**：使用可访问的官方/可信链接；外部信息不是论文正文证据
>
> - **这篇论文是什么类型，和哪些工作相关？**
>   - **论文报告**：方法/理论/系统/基准等类型；依赖、组合、挑战或扩展的工作
>   - **相关脉络**：用 [[笔记#标题|别名]] 或 [[笔记#^block-id|别名]] 跳到已有知识
>   - **尚不能证明**：未覆盖或未读到的相关工作边界
>
> - **作者声称解决了什么当下的问题？**
>   - 用连贯段落交代论文发表时的任务压力、已有方法在什么具体场景或链路失效、作者声称达到的目标，以及这一目标与全文证据之间的边界
>   - 按“当下压力 → 现有失败 → 声称目标 → 证据边界”推进；不要写成新术语清单，不要提前复制 What / Why / How。若作者同时引入多个新模块、表示或约束，允许自然扩写为数段，每段只完成一个叙事任务
>
> - **研究问题审计：Interesting / Solvable / Current level / Impactful？**
>   - **Interesting（问题值得研究吗）**：写清楚矛盾是否真实、非平凡，为什么不是换个数据集即可解决
>   - **Solvable（问题可解吗）**：区分“在论文假设下条件可解”“已有证据部分可解”和“仍未解决”；列出可解所依赖的感知、模型、算力、数据或理论条件
>   - **Current level（当前研究水平）**：说明该问题处于理论奠基、算法竞争、系统集成、工程验证还是规模化部署阶段，并以本论文相对基线与未报告项定位
>   - **Impactful（问题影响大吗）**：说明受益任务/群体、性能或安全后果及证据强度；不能把标题声量当影响证据
>   - **新旧问题/方法分类**：明确判为“新问题新方法 / 新问题老方法 / 老问题新方法 / 老问题成熟方法的新组合”之一，并解释判据
>   - **去重检查**：五项分别只回答“非平凡性 / 可解条件与剩余缺口 / 成熟阶段 / 影响对象与证据强度 / 创新类型”。一个结论只在其唯一语义归属处完整写一次，其他项不得同义改写
>
> - **What / 研究的问题是什么？**
>   - **What did the authors try to accomplish?**：用一句话回答作者试图完成什么
>   - **论文报告**：任务、输入、输出、场景和作者声明的目标
>   - **核心问题**：现有方法具体失败在哪里，为什么重要
>
> - **Why / 为什么要研究？**
>   - **回答**：先用通俗语言说明“不解决什么就无法完成什么”，再给精确定义；证据页码保留在内部台账
>   - **basic idea / 研究思路重建**：只用本文提出前的背景、失败模式、经验观察、理论线索和相关工作，沿已有知识、约束、可行方向走到待检验的 idea；标明来源与推断，不把本文贡献或结果当作前提，也不宣称知道作者实际思考过程
>
> - **How / 使用的方法是什么？**
>   - **What were the key elements of the approach?**：按主链模块逐项写模块任务、输入来源、输入内容、实际处理顺序、输出的物理意义、下游接口、训练阶段与部署阶段的差异、条件与失效边界；论文未报告的字段明确写“论文未报告”
>   - **设计实现与取舍**：解释作者实际选择的结构怎样工作、获得什么和引入什么依赖，再核对它与 Why 中待检验设想的关系；实际方案或验证范围未覆盖该设想时明确指出，不强行对应。复用前述研究路径，不重新讲一遍动机
>   - **关键元素**：按数据流写输入、表示、网络/算法、约束、动作/输出、控制链路和频率
>
> - **用了什么理论？假设是否有效？**
>   - **论文报告**：定义、公式、定理、模型、可行性和成立条件
>   - **可以推断**：实验中是否近似满足
>   - **尚不能证明**：感知漏检、模型误差、离散实现、分布外状态或未覆盖平台的影响
>
> > [!info]- **第一层｜直觉理解 | 一句话本质**
> > - **一句话过程**：只写输入、关键过程、输出和本文用途；只保留理解下一层所需的内容
> > - **现有合格图不修改**：复用唯一主知识笔记中的图；论文位置只在确有必要时嵌入，否则给精确链接
> > - **本层边界**：一句话指出图尚未回答的数学问题
> >
> > ![[AI绘图存放位置/知识点图.png|宽度]]
> >
> > > [!info]- **读图与图例**
> > > - 用 1–3 条说明阅读顺序、颜色或箭头；不重复正文结论
>
> > [!info]- **第二层｜公式与原理：它在数学上怎样成立？**
> > - **公式原文**：写关键原式、编号与整体作用；原文无独立公式时改用伪代码、集合/几何关系、递推或不变量
> > - **逐符号解释与最小推导**：只解释当前计算必需的符号和连接步骤
> > - **检查与回扣直觉**：用一个数值或极端情形检查结果，并映射回图中的对象/箭头
> > - **系统位置与边界**：只写训练/部署位置、软硬属性和最重要的失效条件；同一结论不换句话重复
>
> - **方法具体如何实现？哪些公式或代码细节必须掌握？**
>   - **回答**：必要公式、变量、伪代码、超参数、软件/硬件和未报告项
>
> - **实验 setting 是什么？实验到底支撑了什么？**
>   - **论文报告**：环境、平台、传感器、训练、baseline、指标、消融、样本/场景和结果
>   - **结果卡**：每个主要结果写清对象、仿真/实机条件、样本量、速度/平台与实际 outcome；原文为 N/N 成功时不能缩写成“做了 N 次测试”
>   - **证据分离**：正面/负面结果、样本边界、作者局限和未报告复现项分开写；缺失项不能改写已经报告的结果
>   - **可以推断**：结果支持的最强谨慎结论
>   - **尚不能证明**：实验没有覆盖的更强结论；区分“表现更好”和“理论保证”
>
> - **论文明确承认的局限是什么？**
>   - **回答**：只写作者在正文、图表、失败案例或结论中明确承认的限制；能由图、表、公式或算法精确定位时保留对应编号
>
> - **未报告与疑点是什么？**
>   - **回答**：单列论文没有给出的平台、硬件、参数、样本、训练时长、求解器、视觉链路频率、回退机制或统计信息，并说明为什么影响判断
>
> - **Pros / Cons：优缺点是什么？**
>   - **Pros / 真实价值**：可复用机制、证据强度、工程接口和实际增量
>   - **Cons / 水分与边界**：新增依赖、脆弱假设、复现缺口，以及标题或摘要声称超出证据的部分
>   - **核心贡献最依赖的假设**：突出一个失效代价最大的假设，说明支撑哪项主张、为什么可能失效、论文有什么支持证据或缺口；其他有效局限保留原位置，不重复罗列
>
> - **如何拓展与利用？**
>   - **What can you use yourself?**：指出可直接复用、必须改造和不能迁移的部分
>   - **怎样利用**：可迁移模块、接口、实现顺序和最小复现实验
>   - **怎样拓展**：从作者局限、失败案例和未报告项推出下一步可证伪研究问题；写清变量、对照与成功标准
>   - **最强反例设计**：给一个可区分原解释与替代解释的实验、理论论证或真实场景，交代条件、控制变量、预期判别结果和适用范围；未实施时写“拟议检验”，不能冒充已证实失败
>   - **不能直接迁移**：依赖的传感器、地图、动力学、平台、算力、时延、数据分布和安全前提
>
> - **What other references do you want to follow？还要追哪些参考文献？**
>   - **回答**：列出理论来源、baseline、实现依赖或关键后续工作，并逐条写为什么追
>
> - **是否有 supporting links？**
>   - **支撑链接**：GitHub：...；视频/演示：...；补充材料：...；项目页/数据集：...；没有的类别写“未提供”
>
> - **PDF 原文标注了哪些重点？**
>   - **回答**：按页码概括问题、方法、公式、图表、关键数据、baseline、局限、疑点、support link 和作者外部信息；每项必须存在于 annotation manifest
>
> - **尚未解决的问题是什么？**
>   - **回答**：只列正文、图表、失败案例或作者局限直接暴露的问题；不把猜测写成事实

> [!personal]+ 个人理解
```

## 样式约束

- 模板中的“尚不能证明”“不能直接迁移”等是有条件的证据槽位。只有存在影响当前判断的具体边界时才写出，不为填满模板编造排除项；相同边界在唯一责任位置解释，其他位置用准确短指代。内部证据分类继续保留，必要否定、数值、条件与缺口不得删除。
- 默认中文，专业术语保留准确的英文形式，如 attention、fine-tuning、ablation、retrieval、policy gradient、representation、benchmark；首次出现结合本文解释含义。行文以机制、具体例子和连续推导帮助理解，参照清楚、深入浅出的技术解释特征，不模仿作者身份或编造经历。

- 外层恰好一个 `> [!note]-`
- 内层折叠用 `> > [!info]-`；上下文必须保持同一外层 Callout
- 来源行后放一行单独的 `>`，再开始嵌套 Callout 或列表
- 相邻的两个内层折叠之间必须放一行父级空行 `>`，用来退出前一个内层引用层级、同时继续留在外层 Callout；不要用 `> >` 空行把第二个折叠并入第一个

```markdown
> > [!info]- **概念解释：第一部分**
> > - 第一部分内容
>
> > [!info]- **概念解释：第二部分**
> > - 第二部分内容
```

- 问题和栏目名加粗；回答中的短关键词按 `read-paper-analysis-highlight` 的“论文 Callout 强调语义合同”处理，覆盖问题、输入、方法、机制、设计原因、边界、疑点与量化值，而不是只加粗数字
- 内部证据台账、批注计划和回读记录继续使用一基 PDF 文件页码；完成态 `已AI全文读` Callout 不显示 `（PDF第 N 页）`，只保留准确的 `（公式 X）`、`（图 X）`、`（表 X）`、`（算法 X）`。没有这些结构锚点时不在成品正文补页码
- `==...==` 用于少量可独立复述的完整因果链、方法结论、作者自我限制、决策或条件—结果句；短关键词可以在高亮句中继续加粗
- 核心实验结论可以高亮，但范围应同时包含对象/条件与结果，例如“0.5 m/s 障碍物下 10/10 次无碰撞”，不能只高亮孤立数字
- `<font color="#ff0000">...</font>` 标未提供信息、复现阻断、证据冲突、无效假设或过度主张
- `<font color="#00b050">...</font>` 标有全文证据支撑的正面结果、可复用且已验证的机制
- `<font color="#f79646">...</font>` 标条件与必要检查
- `<font color="#7030a0">...</font>` 标局限与未验证外推
- 颜色与 `==...==` 不叠加；没有对应语义时不得为了凑齐颜色而强行使用
- 每个结论先确定**唯一语义归属**：`一眼记住`只给完整主链，What 只定任务与失败对象，Why 只给设计因果，How 只给输入—处理—输出，理论只讲数学机制与假设，实验只给对象—条件—样本—结果—边界，Pros/Cons 与拓展只给新的综合判断和复用决策
- “作者声称解决了什么当下的问题”只负责把读者带入作者面对的现实/研究压力和声称目标，再由研究问题审计判断价值与证据强度；不能把后续栏目压缩后重复粘贴到这里
- 其他栏目只补充新的机制、条件、证据或边界；不得用同义句在相邻栏目重新陈述。去重不减少事实、条件、数字、局限或复现缺口；没有新增信息时用精确 WikiLink 或“见上文 ××”短指代

- AI 笔记不设机械字数上限。涉及多条新方案、多个相互依赖模块、复杂公式或多组条件时，以读者能沿因果链和数据流顺畅复述为准扩写；优先拆成有自然过渡的短段，禁止为塞全知识点而堆叠名词、括号和并列分号
- 算法、模型、软件/硬件、数据集、API、标准缩写和数学符号默认保留英文；中文翻译生硬、失真或不符合领域惯例时可直接使用英文。首次出现仍要解释该术语在本文中的输入、处理、输出或职责，不能把保留英文当作免解释

- 外层蓝色 AI Callout 与 `> [!personal]+ 个人理解` 之间的源码必须恰好保留一个真实空行；`+` 表示阅读模式默认展开、仍可手动折叠；该空行负责结束蓝色 blockquote，使其成为独立绿色 Callout；通过 `personal-reading.css` 消除视觉留白，两块之间的可见间距必须为 0
- 每次生成完成态 AI Callout 时同步生成或核验个人理解 Callout；不得出现只有 AI Callout、没有个人理解 Callout
- 新建时内部必须为空；新建时只写空的 `> [!personal]+ 个人理解`，不得用占位句、空列表或 AI 总结填充；已有个人理解逐字保留，AI 不得生成、润色、移动或覆盖用户个人内容
- 个人 Callout 的最后一行后直接开始下一篇 `###` 标题，下一篇 `###` 标题前的源码空行必须为 0，即下一篇 `###` 标题前不保留空行；标题本身结束 blockquote，且不得产生额外的可见空白段落
- 个人内容保留在当前核心论文精读笔记中，不得拆分到单独笔记；已有个人 Callout 正文源码必须逐字保留，论文特定个人观点不得写进本模板

### Sheets Extended 表格兼容（按条件启用）

- 若 `.obsidian/community-plugins.json` 显示 `sheets` 已启用，且目标论文笔记包含或将写入普通 Markdown 表格，尤其是 Callout 内表格，则在该笔记的 YAML frontmatter 中写入 `disable-sheet: true`；已有 frontmatter 时只合并该属性并保留其他字段
- 这是当前笔记对 Sheets Extended 原生表格后处理的局部退出；不得全局禁用、卸载插件，也不得改写其他笔记
- 若 `sheets` 未启用，或笔记没有需要保护的普通 Markdown 表格，不得机械添加 `disable-sheet: true`
- 触发症状通常是编辑模式可见，而阅读模式中的 Callout 标题和正文仍在、表格区域为空；优先检查插件状态与 frontmatter，写入后在可用时分别检查 Live Preview 和阅读模式
