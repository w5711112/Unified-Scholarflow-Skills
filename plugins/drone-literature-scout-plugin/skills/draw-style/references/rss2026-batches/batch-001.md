### 2. 图本身表达什么

**精确视觉主张：** 这是一张跨越“数据通信—逻辑 worker—统一硬件抽象—云边物理节点”的分层系统架构图，核心不是某个网络结构，而是说明训练、采样和机器人环境任务如何在异构硬件上被统一调度并交换数据/权重。

按自上而下的阅读顺序：

1. 顶部紫色长条是 `Distributed Data Channel`。标注为 `channel.get` 的向下连接进入 `Train Workers` 和 `Rollout Workers`，表示这两类逻辑 worker 从分布式数据通道取数据。来自两个 `Env Worker` 的连接在上方汇合后以向上箭头进入通道，旁边标注 `channel.put`，表示环境侧把数据写回通道。
2. 中部浅蓝区域是 `Unified Hardware Abstraction Layer`。四类逻辑执行体依次为训练 worker、rollout worker、两个环境 worker；它们共同连接到 `Hardware Registration & Discovery, Hardware Scheduling`，说明上层不直接绑定某一台设备，而由统一层完成硬件注册、发现与调度。
3. 底部虚线紫框是 `Cloud-Edge Tunneling Network`。其中有一台带 A800 的 `Training Node`、一台带 RTX4090 的 `Rollout Node`，以及两台带机械臂图标的 `Robot Node`。右下图例用白/灰填充区分 Cloud 与 Edge；按填充看，训练节点属于 Cloud，其余三个节点属于 Edge。
4. 训练节点与 rollout 节点之间还有一条弯曲箭头，标作 `SM-Budgeted Weight Sync`，箭头朝向 rollout 节点，表达按显存预算约束进行的权重同步。图中没有画出反向同步，因此不能把它解释成已确认的双向机制。
5. 左侧上下两处都写有 `Adaptive Communication Plane`。从版面看，它强调通信机制同时覆盖上层数据通道和下层云边网络；由于截图没有 caption，不能进一步断定这是否是两个独立平面或同一平面的两段表示。

### 4. 全局构图与阅读路径

- 采用三条横向色带组织不同抽象层级，左侧大号斜体层名充当纵向“目录”，读者先识别层，再追踪上下箭头。
- 上层数据通道是一条横跨画布的总线，中层四个逻辑 worker 等距排列，下层四个物理节点与其大致垂直对齐，建立“抽象执行体—物理承载节点”的一一/一对多映射印象。
- 视觉中心是浅蓝色硬件抽象层：它处在数据通道和具体节点之间，且横跨所有 worker，清楚体现桥接作用。
- 底部虚线圆角框只包围物理网络，避免把它误读成软件模块；框内留白用于放置同步箭头和 Cloud/Edge 图例。
- 信息密度中等，主路径是自上而下，局部通信则通过向上和弯曲箭头补充，不需要在多个远端图例之间频繁往返。

### 5. 局部视觉语法

- **形状：** 数据通道与调度层用长圆角矩形，逻辑 worker 用较小圆角矩形，物理节点用带阴影的灰色卡片；同类对象形状稳定。
- **颜色：** 紫色只承担通信平面/网络边界，蓝色承担硬件抽象与逻辑模块，浅绿用于环境 worker，灰度填充承担 Cloud/Edge 部署属性。颜色是类别编码，不是装饰。
- **线与箭头：** 主数据流为黑色正交折线；弯曲箭头专用于权重同步，使其不与垂直调度映射混淆。连接上的 `channel.get/put` 直接写在边旁，而非另做图例。
- **图标：** GPU 与机械臂图标只用于识别设备类型，没有用写实照片抢占注意力；A800、RTX4090 文字提供了关键具体性。
- **字体：** 层名和通信机制为紫色粗斜体，模块名为蓝色常规字体，节点名为深灰；字体层级与颜色共同区分“层—机制—实例”。
- **立体感：** 仅用轻微阴影抬起模块卡片，整体仍是严格的 2D 拓扑图；这里不需要 2.5D/3D，因为图的任务是表达连接和部署关系，而不是几何体积。

### 6. 为什么有效

- 把同一系统的逻辑视图与部署视图放在一张图里，避免读者在软件架构图和硬件拓扑图之间自行对齐。
- 连接文字放在连接本身上，使 `get` 与 `put` 的方向几乎无需 caption 就能读懂。
- 用贯穿全宽的硬件抽象条表达“所有 worker 共享同一种资源发现/调度机制”，比给每个 worker 重复画一个调度模块更紧凑。
- 真实硬件型号、节点类型与抽象 worker 同时出现，使“异构”不是一句口号，而有可见的实例证据。

### 7. 可以吸收的绘图知识

- **新增候选：分层架构的双视图压缩法。** 当知识点同时包含逻辑角色与物理部署时，用水平层带对齐两者，中间设置唯一的抽象/调度桥，而不是画两张互不对应的图。适合分布式学习、机器人集群、边云计算；不适合需要展示时序细节的算法。
- **强化：边标签优先于远端图例。** `channel.get/put` 这类动词直接锚定到箭头，可显著降低歧义；应继续要求箭头文字与线保持净空，不能被线穿过。
- **新增候选：部署属性可用低显著度编码。** Cloud/Edge 只用白/灰填充，主色仍留给功能类别，避免一个对象同时被多套高饱和颜色争抢。
- **强化：具体硬件只写识别所需信息。** A800、RTX4090 与机械臂图标足够支持语义，不需要画复杂机箱照片。

### 8. 不足、误读风险与不应照搬

- 上下两处重复的 `Adaptive Communication Plane` 容易让人误判为两个同名层；若用于自己的图，应通过贯通括号、统一外框或一次性标题明确它是一个跨层关注面还是两个实体。
- 从调度条到物理节点的多根近距离箭头较密，部分映射关系需要仔细追线；自己的图应避免在一个窄区域内出现平行线交叉或过近。
- Cloud/Edge 仅靠白/灰填充，缩小或灰度打印时仍能区分，但图例离节点较远；可在节点角标直接加 `Cloud/Edge` 以减少回看。
- 顶部和底部通信机制的精确协议、调度算法、同步频率都没有展示，不能从这张架构图推断实现细节。

### 9. 本图最值得学习什么（收录理由）

这张图最值得吸收的不是某一种分布式学习拓扑，而是**柔和而有层次的科研架构图外观**：相邻浅紫、浅蓝、米白、浅绿之间色差克制，功能仍可分辨；左侧窄文字区与右侧宽流程区比例稳定；同类卡片尺寸、间距和垂直对齐统一；低强度投影给模块适当高级感而没有变成网页 UI。后续画系统架构总图时，应优先复用这套“浅近邻色 + 统一轻阴影 + 大小区域明确分工”的视觉逻辑，而不是机械复刻其具体 worker 数量。

### 10. 证据边界

- 领域标签来自图中 worker、GPU、机器人节点等可见线索，不等于论文官方分类。

### 2. 图本身表达什么

**精确视觉主张：** 图展示一条“图像预测无绝对尺度的点云 + IMU 提供米制尺度信息 → 闭式线性初始化 → 仅优化尺度与 IMU 状态的无特征 VI-BA → 启动 VINS 跟踪”的完整系统链。

caption 明确给出的语义与图形对应如下：

1. 左上多帧 `Images` 进入 `Feed-forward model`，得到位于初始相机坐标系 (C_0) 中的点云。caption 明确称这些黄色元素为模型预测的 **up-to-scale point clouds**，即几何形状已有，但绝对尺度尚未确定。
2. 左下 `IMU meas.` 经过 `Preint.`，绿色虚线串联的多姿态小坐标架表示 IMU 预积分位移 ({}^{I_0}\Delta p_{I_i})。caption 明确说它提供 metric-scale IMU information。
3. 中央灰色点云、黄色预测点/虚线、红蓝绿坐标轴和绿色轨迹把视觉几何与惯性运动放在同一 3D 场景中。它直观说明两类信息不是简单拼接的向量，而是在共享空间关系中共同约束尺度、速度和重力。
4. 下方给出 feature-free 线性系统：
   
   \[
   \bar A_{i,m}({}^{C_0}\bar p_{O_{i,k}})\,\mathbf x
   =\bar b_{i,m}({}^{I_0}\Delta p_{I_i}),\qquad
   \mathbf x=[s,{}^{I_0}\mathbf v_{I_0}^{\mathsf T},{}^{I_0}\mathbf g^{\mathsf T}]^{\mathsf T}.
   \]
   
   caption 进一步解释：左侧矩阵吸收 up-to-scale 点云几何，右侧向量编码米制 IMU 信息；未知量包含尺度 (s)、初始速度和重力。
5. 右侧 `Feature-free VI-BA` 因子图中，顶部尺度节点 (s) 通过橙色 `Scale Const.` 与多个图像状态 (x_{I_0},x_{I_1},x_{I_2},\ldots,x_{I_{N-1}}) 相连；相邻状态之间由绿色方形 `IMU Pre.` 因子连接。caption 明确说该紧凑 BA 只涉及 scale 与 IMU states，随后用于 bootstrap `VINS Tracking`。

图没有声称已经展示完整 VINS 后端；它展示的是启动跟踪之前的初始化与精炼过程。

### 3. 逐元素与连接核读

**逐元素账本：**

- 左上 `Images` 下方是四层可见的灰度图像叠片，前景图含棋盘格目标和室内家具；其右侧 `Feed-forward model` 下方用深蓝、浅蓝和黄色竖向块表示网络，未展开层名。
- 左下标题由绿色粗体 `IMU` 和黑色 `meas.` 组成，下方是 InertialSense 设备照片；右侧 `Preint.` 配一条绿色虚线运动链，链上有三个可辨识的蓝灰刚体/IMU 坐标架，每个坐标架带黑灰方向箭头。
- 中央标题为黄色粗体 `Point cloud`、黑色 `in C_0 frame`，右上黄色公式标签为 ‎\({}^{C_0}\bar{\mathbf p}_{O_i,k}\)。主体是一幅浅灰室内稠密点云。
- 点云场景中可分辨出 11 个黄色菱形点标记；四个红—绿—蓝局部坐标架沿一条绿色弯曲轨迹排列。黄色/橙色虚线把菱形点与对应位姿连接，表示可见的几何关联；虚线没有箭头头部。
- 场景下方左侧文字为两行 `Feature-free / linear system`，右侧完整公式为
  \[
  \bar{\mathbf A}_{i,m}({}^{C_0}\bar{\mathbf p}_{O_i,k})\mathbf x
  =\bar{\mathbf b}_{i,m}({}^{I_0}\Delta\mathbf p_{I_i}),\quad
  \mathbf x=[s,{}^{I_0}\mathbf v_{I_0}^{\mathsf T},{}^{I_0}\mathbf g^{\mathsf T}]^{\mathsf T}.
  \]
  点云变量保持黄色，IMU 预积分变量保持绿色。
- 右侧标题 `Feature-free VI-BA` 下方是因子图：顶部一个白色圆节点 (s)；底部四个白色圆状态节点 (x_{I_0},x_{I_1},x_{I_2},x_{I_{N-1}})；从 (s) 向四个状态节点各有一条橙色边，边上各有一个橙色圆形因子；相邻状态之间共有三个绿色方形因子。
- 因子图下方由两条黑色水平分隔线夹出图例区：橙色线—圆标记写 `Scale Const.`，绿色线—方块写 `IMU Pre.`。
- 最右上是 `VINS Tracking`，旁边有一个白底黑边、指向右上方的粗空心箭头。
- 最下方 caption 逐字说明：feed-forward 3D model 从输入图像预测黄色 up-to-scale point clouds；IMU measurements 以绿色表示并预积分；二者形成 feature-free closed-form linear system；\(\bar A\) 编码点云几何、\(\bar b\) 编码米制 IMU 信息；闭式解经只涉及尺度和 IMU 状态的 compact feature-free bundle adjustment 精炼，最终 bootstrap VINS tracking。

**箭头/连线账本：**

- 图像叠片 → `Feed-forward model`｜空间邻接，无单独箭头｜无边标签｜图像是模型输入，正式定义由 caption 提供。

### 4. 全局构图与阅读路径

- 2×2 矩阵同时控制两个比较维度：列固定状态类型（translation/rotation），行改变基线（CLOSURE/GRCC）。蓝色 Ours 在四格中保持不变，使读者每次只比较一个基线。
- 左列统一为斜俯视多面体/复杂体，坐标约在 (X=0.18\!\sim\!0.21,m)、(Y=0.75\!\sim\!0.78,m)、(Z=0.595\!\sim\!0.62,m) 的局部范围；右列统一为球体视图，轴值范围也在上下两格保持一致。刻度仅用于定位与尺度，不应从截图读取超过其显示精度的数值。
- 四个面板面积接近、相机角度和留白一致，caption 位于整组图下方；没有额外大标题占据绘图区。
- 每格都放局部图例，牺牲少量重复换取单格截图时仍可独立理解。

### 5. 局部视觉语法

- **方法颜色：** 蓝色始终是 Ours，桃色始终是 baseline；方法颜色跨平移/旋转、跨两种基线保持一致。
- **几何形状：** 多面体用半透明面 + 黑色棱边；球/圆滑集合只用半透明表面。图形外观忠实保留各方法输出集合的几何类型，没有为了统一美观强制画成同一种形状。
- **空间比较：** 所有结果共中心或高度重叠，适合比较外包络和局部突出；透明度使内部集合仍可见。
- **轴与单位：** 左列标 `X(m), Y(m), Z(m)`；右列只显示 `X, Y, Z`，截图中未见旋转单位。正式复用时应明确旋转参数化及单位。
- **线条与网格：** 坐标网格极淡，黑色多面体棱边是唯一高对比结构；球体表面有柔和高光/透明叠色，但没有厚重阴影。
- **字体和图例：** 轴标签、刻度和图例都使用较小论文图字号；下标 (t/R) 区分平移/旋转结果。

### 6. 为什么有效

- 通过矩阵布局把“状态类型”和“比较基线”正交化，避免四张散图要求读者记忆前图条件。
- Ours 的颜色和几何表示跨面板固定，使注意力集中在 CLOSURE 与 GRCC 的变化，而不是重新学习编码。
- 左列保留多面体和复杂基线集合的真实形状，右列则利用同心球快速传达旋转范围；没有为了风格统一牺牲语义准确性。
- 透明叠加让“谁在内部、哪里突出、形状是否一致”可被视觉检查，这是二维轮廓图难以完整表达的三维关系。

### 7. 可以吸收的绘图知识

- **新增候选：二维比较因素用图矩阵正交展开。** 列固定变量类型、行固定基线或阶段；每个面板只改变一个因素。适合论文结果图，也可用于 Obsidian 的算法对比知识图。
- **强化：保持方法颜色，不强求几何同形。** 比较集合方法时，颜色编码方法，形状忠实编码实际集合；准确性优先于视觉整齐。
- **新增候选：共享相机与轴域是 3D 比较的硬门槛。** 只有角度、轴范围、纵横比一致时，才能允许读者比较相对体积。
- **细化：重复图例可按使用场景处理。** 论文中单格可能被引用时可保留局部图例；PPT/Obsidian 整体展示时可改为一个全局图例并增加行列标题，节省空间。
- **强化：代码绘图也需要二维排版设计。** 即使每格是 MATLAB/Python 生成的 3D 坐标图，最终仍要统一四格尺寸、相机方位、轴范围、图例位置和行列间距，不能把四张默认输出直接拼接。

### 8. 不足、误读风险与不应照搬

- 图没有明确的行标题，读者必须从每格图例判断上排是 CLOSURE、下排是 GRCC；自己的图应优先加简短行标签并合并图例。
- 右列没有可见旋转参数化/单位；若球体处于李代数、欧拉角或其他空间，必须在 caption 或轴标签中说明，不能只写 X/Y/Z。
- 透明体的包含关系会受视角和 alpha 影响，左下复杂桃色体尤其容易发生遮挡；严谨结果最好配套给集合体积、覆盖率或二维切片。
- 蓝色集合视觉上更大并不自动等于更好；不应把“外层”用胜利色或强化阴影暗示性能结论，除非论文指标定义支持。

### 9. 本图最值得学习什么（收录理由）

这张图延续 004 的学习重点：用半透明三维几何体表达不确定性集合，同时保证坐标轴、刻度、单位、视角和遮挡准确。它额外提供了一个更重要的正式论文数据图范式：**用 2×2 矩阵把“变量类型”和“比较基线”两个因素正交展开**。后续绘制多方法、多状态的 3D 结果时，应先锁定每列的坐标与相机，再改变每行的基线；方法颜色保持一致，集合真实形状不为排版整齐而被改写。

### 10. 证据边界

- 未从截图确认 CLOSURE、GRCC 的完整名称与算法定义，平移/旋转集合对应的置信水平，以及集合大小的评价准则。
- 未确认四格是否使用完全相同样本、相同目标置信度或相同归一化方式。
- 只能报告可见的相对形状/包络，不从视觉外推覆盖率、紧致性最优或计算效率。

## 本批综合

### 1. 视觉家族

本批不是一种“浅色圆角框图”风格，而至少包含四类可独立选择的视觉家族：

1. **分层系统/部署架构**（RSS2026_001）：强调抽象层、逻辑角色和物理承载关系。
2. **跨表示系统总览**（RSS2026_002）：真实输入、3D 几何、公式与因子图在一条因果链中逐层抽象。
3. **高密度神经网络方法主图**（RSS2026_003）：大阶段容器 + 多模态支路 + 训练专用监督路径。
4. **3D 集合与不确定性结果图**（RSS2026_004–005）：用透明体、边界和统一坐标系展示包含、重叠、外扩和形状差异。

因此 `draw-style` 不能把顶刊风格收敛成单一配色或单一盒子模板；应先判断视觉命题属于拓扑、因果链、训练架构还是空间集合比较，再选择完全不同的图形语法。

### 2. 共同有效原则

- **语义必须跨区域保持：** 通信紫、点云黄、IMU 绿、训练棕、Ours 蓝等都不是局部装饰，而是贯穿对象、连接、公式和图例的稳定编码。
- **宏观分区先于局部细节：** 横向层带、三阶段大容器、2×2 矩阵都先回答“整图分几部分”，再允许局部高密度。
- **形状承担真实含义：** 状态节点/因子、点/面/边、多面体/球体都不可随意互换；视觉整齐不能覆盖方法真实几何。
- **caption 与图内分工：** 图内负责对象、关系和读图入口，caption 负责正式定义、训练/推理边界和结论口径。不能把 caption 长句全部塞回图中。
- **复杂图仍控制局部变化因素：** RSS2026_003 的训练支路、RSS2026_005 的行列比较都让每个局部只改变一个明确因素。

### 3. 条件冲突而应并列保留的原则

- **2D 拓扑 vs 3D 几何：** 架构和因果流用 2D 可获得最高可读性；体积、包络、遮挡与坐标关系必须用 2.5D/3D。两者不是统一风格问题，而是语义选择问题。
- **统一图例 vs 局部图例：** 整体连续阅读可用全局图例；面板可能被独立引用时，局部图例更自包含。应按媒介决定，不设绝对规则。
- **淡色大底 vs 纯白数据底：** 阶段架构可用淡色容器帮助分区；定量/空间结果图应保持白底、淡网格，避免底色干扰数据。
- **照片/真实点云 vs 纯示意图元：** 输入模态需要具象锚点时可嵌入小型真实图；若只表达拓扑，图标已足够，照片会增加噪声。

### 4. 对不同输出场景的候选影响

- **PPT：** 可吸收 RSS2026_001 的分层层带与 RSS2026_002 的跨表示颜色，但必须减少变量和小字号；每页只保留一个视觉主张。
- **Obsidian 知识点：** 优先借鉴 RSS2026_002 的“来源—原理—状态/输出”链和 RSS2026_004 的单一空间包含关系；不应照搬 RSS2026_003 的全量四尺度与所有训练支路。
- **正式论文方法图：** RSS2026_002–003 提供完整方法图模板：阶段容器、训练/推理双路径、跨表示颜色、公式位于因果节点、caption 补正式定义。
- **正式论文数据/结果图：** RSS2026_004–005 强化 3D 集合比较规范：真实单位、透明度 + 边界补偿、共享视角/轴域、不得仅凭视觉包络替代覆盖率或体积指标。

### 5. 等待确认的 `draw-style` 候选规则

1. 增加“视觉命题路由”：拓扑/部署→2D 分层；跨模态求解→跨表示链；空间集合→2.5D/3D；双因素比较→矩阵布局。
2. 增加“语义颜色跨表示一致”规则，并限制一类信息只分配一个稳定颜色。
3. 增加训练专用路径规范：单一辅助色 + caption 明示；灰度风险高时再加虚线/角标。
4. 增加 3D 集合图硬验收：物理单位、共享相机、共享轴域、透明面边界补偿、定量指标或切片作为必要补充条件。
5. 增加符号解释门槛：非通用雪花、彩色 query 条、特殊节点若无法就地自解释，必须进图例或 caption。

以上均是本批候选，不在用户确认前修改稳定参考文件。
