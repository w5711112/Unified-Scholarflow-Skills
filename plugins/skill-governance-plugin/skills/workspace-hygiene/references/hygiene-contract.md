# Workspace Hygiene Contract

Use the fixed `HYGIENE_REQUEST` object to name the workspace root, policy, selected proposal paths, quarantine root, and approval tokens. `scan_workspace(root, policy)` returns `ScanReport`; `build_proposal(report, selected_paths)` returns `HygieneProposal`; `apply_proposal(proposal, quarantine_root, approval_token)` returns `HygieneResult`; and `purge_quarantine(result, approval_token)` returns `HygieneResult`.

`Candidate` contains relative path, size, category, reason, and action. Reports expose automatic candidates, proposal candidates, protected paths, and total bytes. Proposals expose their root, candidates, protected paths, and expected bytes. Results expose changed paths, action, reasons, before/after byte totals, rollback path, and residual risks. A dry run is scan plus proposal: it changes nothing and provides the candidate, size, reason, action, protected-path, and expected-byte fields needed for review.

Only mechanical files may be automatic deletion candidates: files below `__pycache__`; `.pyc` or `.pyo` files; `.pytest_cache` contents only when the policy records successful test completion; and a task-owned temporary path only when policy records its successful producer. After every automatic file has been safely disposed, remove only now-empty directory ancestors through the enclosing `__pycache__` or `.pytest_cache`; a later evidenced automatic pass may also remove those already-empty cache directories without creating a quarantine package. Never remove the surrounding source or test directory, and report a nonempty or raced directory as residual risk. A semantic-only transaction sets `automatic_cleanup` to `false`, which protects every unrelated automatic candidate instead of adding it to the proposal. Without the required evidence, cache and temporary paths remain protected. Delete no semantic content automatically.

`legacy`, `backup`, `backups`, `archive`, `old`, `output`, and `node_modules` are proposal-only. A policy may additionally name already-reviewed files through `semantic_candidate_paths`, but each value must match one exact relative file path; it cannot select a directory, prefix, wildcard, or unknown sibling. Proposal candidates may only be moved to quarantine after the exact proposal token `APPROVE:<sha256(canonical proposal JSON)>` is supplied. Test source files, `python-packages`, `.git`, `.skill-contract`, incident registries, and every unknown path are protected. Mechanical `__pycache__`, `.pyc`, `.pyo`, and evidenced `.pytest_cache` entries remain automatic candidates even when nested under `tests`; the surrounding test sources stay protected. All other protection wins over automatic or proposal classification, including an exact-path request; `python-packages` remains protected even when omitted from policy.

Classification precedence is fixed: hard protection, mechanical cache or declared task-temporary handling, test-source protection, exact semantic candidates, then proposal-name heuristics. An exact semantic path therefore cannot reclassify a mechanical cache or declared task-temporary path.

Only tool-created scan reports can build executable proposals. Apply rescans using the recorded policy and rejects any caller-supplied candidate, category, action, path, size, or candidate digest that differs from the current canonical proposal. The approval token still binds the complete reviewed proposal, including its protected-path snapshot, while unrelated protected-path drift does not invalidate unchanged candidates; the fresh protected set always wins during execution. Before any move or delete, preflight every candidate: the source must exist and resolve inside the scanned root, no currently protected path may be selected, no reparse point may occur on source or quarantine paths, the quarantine root must resolve outside the scanned root, and no target may already exist. Immediately before mutation, revalidate path identity and containment; on a move failure restore every completed move, retaining explicit recovery evidence if restoration cannot complete. Quarantine retains each relative path and a tool-generated manifest, so it remains reversible; do not place it inside the scanned/synchronized root, where it would remain in the same sync volume and could be rescanned recursively.

Directory traversal stops at every reparse point and at every directory that cannot be safely enumerated. The boundary entry itself is reported as protected, and no descendant reached through a symlink, junction, or unreadable directory may contribute candidates, protected descendants, hashes, or workspace byte totals. On Windows, verified quarantine creation and handle acquisition use the extended-length native namespace while the manifest retains ordinary absolute and relative paths, so deep approved paths remain reversible without shortening their identity.

Verify the before and after workspace byte totals, keep residual risks explicit, and rescan after execution. Purging quarantine is a distinct irreversible operation requiring exactly `PURGE:<sha256(resolved quarantine path)>`; an `APPROVE:` token never authorizes purge. Purge accepts only a tool-created live quarantine whose manifest and entries remain complete and whose boundary is outside its scanned root; it never deletes a protected, unknown, or caller-selected directory.

When the collect-bug-update-accelerate guard applies, do not scan the quarantine as part of the original root. Record real cleanup failures through its required capture route before changing routes, and preserve the incident registry as protected.

## Latest validated build and scheduled retirement

Keep the latest accepted result and its complete build dependency closure: builder, configuration, templates/assets, required inputs and reproducibility evidence. A larger version number, newer mtime or generated output alone does not establish acceptance. A failed v1.5 does not retire accepted v1.4; an older builder still used by the current version remains protected. Tests and fixtures are dependencies until proven otherwise.

Protect every academic-native-*ppt* Skill variant and `_ppt-shared-assets`; register these names in every scheduled policy. Unknown user files, active task files, candidate-pool decisions and source evidence are protected. Scheduled scans are limited to explicitly registered roots and producer-owned artifact manifests, never a drive or user-home sweep.

For an approved recurring policy, the producing owner may nominate exact superseded artifact paths with content hashes, a verified successor and a retained dependency list. Hygiene validates those facts and produces the same exact proposal; incomplete evidence stays proposal-only. First run is dry-run. Semantic quarantine and purge continue to require the existing exact tokens: recurring scheduling alone never fabricates approval. A user-approved policy may only automate actions whose exact scope and current evidence are represented in that approval; new paths or changed contents require review.

Suggested retention is seven days for superseded reproducible artifacts and fourteen days for one recovery snapshot outside the active/synchronized root, subject to the user's adopted policy. Age never overrides dependency, acceptance or protection. Until an executable, tested retention authorization is present, scheduled maintenance performs mechanical cleanup and proposes semantic retirement without purging it. Report this boundary rather than claiming historical scripts were automatically removed.
