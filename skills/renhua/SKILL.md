# renhua：简体中文人性化改写

把文本从“模型在表演写作”拉回“一个人在把事情说明白”。改写是重写表达，不是删掉实质内容，也不是把所有文本改成同一种语气。处理后应不卑不亢、自然克制、逻辑闭合、上下文准确，让目标读者容易理解。

## 权威与架构锁

- 当前用户明确要求优先；本文件与适用直接参考共同构成权威。计划、摘要、清单、测试和评分均不能替代原规则。
- 主 Skill 是唯一内容源；`renhua-draft` 必须与主运行包字节级对齐，不能反向覆盖主规则。
- 架构版本为 `route-b-v3`。本版本在既有单层路由中加入普通文本与对话场景，并把不卑不亢、来源/承诺边界、跨文档一致性和表格真实居中纳入原责任文件；不增删证据对象、一级参考或规则编号。以后新增内容只写入对应责任参考并更新权威映射/回归测试；未经用户明确批准，不增删证据对象、一级路由或加载条件，不把规则正文堆回入口。
- 五条质量底线不变：事实与强度守恒、语体与姿态相称、篇幅不设指标、不做身份表演、输出洁净。按词句承担的动作判定，先做误杀防护；清单不是穷举。

## 适用边界与场景

- 适用于已有简体中文文件、段落和对话，包括论文、知识点笔记、基金本子、严谨工作文档、普通说明、邮件/消息、公众号与口播稿。它只处理表达；事实研究、专业论证和逐字翻译仍由相应任务或专业 Skill 负责。生成或修改简体中文 Obsidian 笔记或 Word/WPS 正文时，推荐顺序为 `专业语义草稿 → renhua → 格式 Skill`。
- 默认 `general-text`；论文/知识笔记转 `paper-notes`，基金信号转 `grant-proposal`，职责/流程/验收/规范助词信号转 `work-doc`，明确保留说话轮次或形成回复时转 `dialogue`。场景豁免优先于编号规则，规则冲突时编号小者优先。
- 文本无规则命中时说明并原样返回；改写数量、缩短比例、词汇替换数和检测器评分都不是质量指标。

## 单层路由

按可观察条件读取适用参考一次；输入、场景和输出类型未变时复用。**直接参考不得继续路由第二层参考**。规则归属不确定时读取两份规则参考，不能为节省上下文跳过不确定项。

| 读取时机 | 唯一职责 | 直接参考 |
| --- | --- | --- |
| 每次改写前 | 五条铁律、五场景、冲突优先级、来源/承诺边界、受保护内容 | `references/core-authority-and-scenarios.md` |
| 命中标点、翻案/判断句、开收尾套话、排比、夸饰、无源引用 | R1–R8 的完整命中、豁免、示例和数值 | `references/rewrite-rules-r1-r8.md` |
| 命中名词化、主语/回指、节奏、黑话、对话/上下文残留、术语、逻辑、段落模板 | R9–R17 的完整命中、豁免、示例和数值 | `references/rewrite-rules-r9-r17.md` |
| 每次交付前 | 三步执行、默认输出、六项交付门禁 | `references/execution-and-delivery-contract.md` |
| 写入 Word/WPS 或任务包含表格 | 三线表、单元格、缩进、对齐、相邻表格 | `references/document-table-format.md` |

规则轻扫只分类，不直接改写：R1–R3 看标点预算、翻案对称和后置判断；R4–R8 看开收尾、排比、夸饰和无源引用；R9–R12 看名词化、主语/节奏与黑话密度；R13–R14 看对话及上下文泄漏；R15–R17 看术语、逻辑和段落模板。同义变体按功能归入现有编号。

## 单一证据脊柱

只维护五个对象；上游未变时不得重建，变化时**只刷新受影响对象及下游**。

| 对象 | 必含内容 |
| --- | --- |
| `SOURCE_BASELINE` | 原文、用户范围/输出偏好、场景、目标读者、不可改结构；存在权威材料时含其优先级与承诺边界 |
| `PROTECTION_LEDGER` | 人物、数字及修饰对象、时间、术语、符号/公式、引语/归因、限定/强调、职责/承诺、引用/标题 |
| `EDIT_LEDGER` | 每处改动及 R 编号、原/新片段、整句姿态删除、待补信息 |
| `READTHROUGH_RESULT` | 连贯与洁净残留、定义顺序、删句波及、场景一致性 |
| `DELIVERY_ACCEPTANCE` | 保真、洁净、连贯、呈现、语域、可审计六项结果与输出包 |

依赖为 `SOURCE_BASELINE → PROTECTION_LEDGER → EDIT_LEDGER → READTHROUGH_RESULT → DELIVERY_ACCEPTANCE`。规则命中当场记账，最终只做一次保真对账和一次交付判定；禁止把同一要求拆成多个子部分反复验证。

## 三步执行，不多跑

### 1. 主循环

先冻结基线、判场景和目标读者、划受保护内容并建术语表；有权威材料或多文档体系时，同时冻结来源优先级、文档职责和承诺边界。再按 `R17 → R4/R5/R8/R13/R14 → R2/R3/R6/R9 → R1/R7/R12 → R10/R11/R15/R16` 把全文过一遍。命中即改并记 R 编号；这是一个循环内的顺序，不是每条规则各扫全文。专业 Skill 已写出的事实与算法结构属于基线，renhua 只负责让表达可读，不能自行补足原文没有报告的领域事实。

删句时立即检查后文指涉；拆并句时立即检查主语、限定、强调和引用归属。对应不了规则的改动撤销；原文的可疑因果、无源引用、未定义术语和作者占位符不静默补写。

### 2. 一轮通读

仅查连贯（R10/R11/R15/R16）和洁净（R13/R14），形成 `READTHROUGH_RESULT`。发现问题按原编号局部修复并更新下游，**禁止重新发起全文重扫**。

### 3. 对账输出

逐项找回 `PROTECTION_LEDGER`，确认事实、职责、承诺、限定、强调、引用和结构零漂移，每个新增实词必须能回指原文或用户明确要求。随后读取交付合同并生成一次 `DELIVERY_ACCEPTANCE`；用户说“只要正文”时仅给改写稿，否则按默认三部分交付。Obsidian 格式 Skill 或 Word/WPS 排版在语言闸门通过后执行；格式步骤若新增了实质性正文，新文字必须重新经过 renhua。Word/WPS 或表格任务再读取表格合同，格式处理不得改变正文语义。

## 停止与失败

- 原文缺失/不可读、任务不适用或用户要求与事实守恒冲突时停止说明，不猜测正文。
- 无源引用依赖来源、原文因果可疑、术语未定义、材料单薄或占位符是作者待办时，保留必要原文并列入“待确认/需补信息”，不得虚构补齐。
- 门禁失败先按对应 R 编号局部修复；无法在不改变事实与强度的前提下修复时交付保守版本，并明确待确认项。成功只由 `DELIVERY_ACCEPTANCE` 判定。

## 维护与主草稿对齐

- 主包修改后，同步 `SKILL.md`、五份直接参考和 `authority-map.json` 到草稿包，并用 SHA-256/二进制比较确认一致；两边同时变化时停止并人工合并。
- 新增场景、规则编号、证据对象、一级参考或改变加载条件属于架构变更，须先获用户明确批准，再更新架构版本和迁移测试；普通规则增量不得借机改变这套高效结构。
